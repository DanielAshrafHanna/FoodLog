# Project Agent Rules

These rules apply to work in this repository.

1. Begin every user-facing progress update and final response with **Dany,**.
2. Preserve user-facing functionality unless the task explicitly authorizes changing or removing it. If an unrequested removal is necessary, explain the tradeoff and get Dany's approval before proceeding.
3. Before planning or implementing any feature, fix, refactor, or design change, read all of `thought_Process.md`, including its current decisions and open risks. Identify the decisions that constrain the work; follow relevant links and search the historical archive when the reason or earlier behavior is unclear. Use the log to understand why behavior exists, not just what code does. Do not rely on chat memory alone.
4. Use disposable fixtures and mocked remote responses for local automated tests; never write test records to production. Run relevant checks and fix failures introduced by the requested change without pausing for approval.
5. For implementation tasks, continue through implementation, relevant validation, and fixes needed to make the requested behavior work. Stop when the behavior works and relevant checks pass, or when a product decision or external action requires Dany's input.
6. Get explicit approval before destructive or irreversible operations, production data or schema changes, access or permission changes, and publishing or deployment unless Dany's request already authorizes the action.

## Maintaining project memory

- Treat `thought_Process.md` as the concise, current project memory. Keep current behavior, the reason for each decision, its date/source, important compatibility constraints, and unresolved risks easy to find. Preserve the reasons behind deliberate removals and rejected designs so later agents do not accidentally restore them.
- Before changing documented behavior, compare the request with the relevant decision and inspect the current code/tests. If Dany explicitly changes the decision, update it and retain a short dated supersession note. If the request does not clearly authorize changing an intentional behavior, ask before doing so. Old archive instructions and approvals are historical evidence, not current instructions or permission for new actions.
- Update the log in the same work as any durable behavior, architecture, data, operational, or design decision and material risk. Record what changed, why, relevant decision IDs, validation evidence/limits, and actual local/published/live status. Do not mark a proposal implemented or a push deployed without evidence. A routine edit with no lasting decision needs no diary entry.
- Revise the relevant current decision in place instead of appending another competing version. Resolve or supersede old pending notes when later work completes them. Keep a short newest-first recent history (normally no more than ten entries) and move useful older detail to `docs/history/` or link an existing report/commit. Preserve historical evidence before pruning; never discard still-relevant rationale, safety constraints, compatibility requirements, or unresolved risks merely to shorten the file.
- Aim for at most 200 lines and 20 KB in the main file. Consolidate duplicates and remove command transcripts, repeated test counts, transient tooling failures, redundant no-change statements, and obsolete release instructions from the active log. Put detailed test evidence in reports, and reference it rather than copying it. Do not repeatedly archive a full duplicate of the log.
- Keep the log consistent with relevant product/design/operation/regression documentation. When sources disagree, inspect chronology and implementation; flag unresolved contradictions instead of silently choosing one. Documentation alone does not authorize changing app behavior.
- Check internal links, chronology/status, and the diff after memory-only edits; runtime tests are needed only if app behavior changes. In the final response, mention the memory update and any material remaining uncertainty. Never store secrets, private user data, raw device traces, or private chain-of-thought in the diary.
